# MAX: учет рабочего времени

Работающий Python-проект для личных диалогов с ботом MAX. FastAPI принимает Webhook, PostgreSQL хранит сотрудников, смены, перерывы, заявки, аудит и постоянные очереди. HTTP-адаптер MAX отделен от расчета времени и бизнес-операций. Интерфейс бота — на русском.

Актуальная официальная документация изучена **02.11.2026**. Контракты, ссылки и ограничения собраны в [docs/MAX_API.md](docs/MAX_API.md). Используется `platform-api2.max.ru`, токен в заголовке Authorization, Webhook с секретом, inline callback-кнопки, загрузка CSV через подтвержденный `/uploads`. Непроверенных SDK и вымышленных методов нет.

## Возможности

- Регистрация: запуск → ФИО → одобрение администратором. Администраторы с разрешенным доступом получают личное уведомление с ФИО, MAX ID и командой одобрения; повторная подача ожидающей заявки не создает новое уведомление. Администратор должен предварительно открыть диалог с ботом и отправить `/menu`. `/id` показывает только собственный стабильный MAX user_id, в том числе до одобрения.
- Шесть кнопок: «Начать работу», «Начать перерыв», «Закончить перерыв», «Завершить работу», «Мой статус», «Мои часы». Есть текстовые команды.
- В ответе на действие — время события и состояние; при завершении — полная длительность, перерывы, чистое время. Завершение во время перерыва закрывает его той же отметкой.
- Личные часы за сегодня, календарную неделю с понедельника, месяц, включительный диапазон дат. Все незакрытые смены показываются отдельно и не входят в итоги.
- Администратор одобряет и блокирует сотрудников, видит открытые смены и отчеты по всем либо одному сотруднику; получает CSV непосредственно в личном MAX-диалоге.
- Исправление завершенной смены по заявке с причиной. Применение после одобрения, проверка версии и пересечений. Аудит хранит автора заявки, администратора, дату, причину, старые и новые значения.
- UTC в БД (`timestamptz`), часовой пояс организации через IANA `ORG_TIMEZONE` (по умолчанию Asia/Omsk). Смены через полночь и переходы летнего времени рассчитываются по UTC-интервалам.
- Защита от повторной доставки событий и одновременных нажатий, атомарные транзакции, PostgreSQL partial unique indexes для открытой смены/перерыва.
- Геолокация, мониторинг активности и зарплата отсутствуют.

## Подключение MAX и запуск

Нужны Docker с Compose v2, домен и HTTPS reverse proxy на порту 443 с сертификатом доверенного CA. Сначала можно запустить контейнеры без реального токена; для обмена сообщениями он обязателен.

1. Создайте/подключите бота на [MAX для бизнеса](https://business.max.ru). Выполните требования платформы к профилю и доступу к созданию ботов. Токен находится: **Чат-боты → нужный бот → ⋮ → Настройки**. Для ботов, созданных в мини-приложении «MAX для бизнеса», документация также допускает получение токена там или через соответствующего бизнес-бота командой «Получить токен». См. [авторизацию MAX](https://dev.max.ru/docs-api).
2. В каталоге проекта выполните:

   ```bash
   cp .env.example .env
   python -c 'import secrets; print(secrets.token_urlsafe(32))'
   ```

   Сохраните сгенерированный секрет как `MAX_WEBHOOK_SECRET`. Укажите `MAX_BOT_TOKEN`, числовой `ADMIN_MAX_ID`, `PUBLIC_BASE_URL`, `ORG_TIMEZONE`. Замените пароль PostgreSQL и в `POSTGRES_PASSWORD`, и в `DATABASE_URL`; специальные символы в URL нужно percent-encode. Для Compose имя сервера в URL — **db**, для отдельного локального Python — **127.0.0.1**. `.env` не включается в Git.
3. Если ваш MAX ID неизвестен: временно оставьте заведомо неиспользуемое значение `ADMIN_MAX_ID`, запустите приложение и подпишите Webhook по следующим пунктам. Отправьте боту `/id` из своего личного диалога. Перенесите полученный ID в `.env`, пересоздайте web/worker (`docker compose up -d --force-recreate web worker`) и отправьте `/menu`. Администратор назначается только по настройке сервера, а не по ФИО/телефону. Не используйте для начального значения ID другого реального сотрудника.
4. Запуск (миграции выполняет отдельный одноразовый сервис):

   ```bash
   docker compose up -d --build
   docker compose ps -a
   docker compose logs --tail=50 web worker migrate
   curl http://127.0.0.1:8000/health
   ```

5. Настройте HTTPS-прокси снаружи контейнеров: `https://bot.example.ru/webhook` → `http://127.0.0.1:8000/webhook`. Прокси должен сохранять `X-Max-Bot-Api-Secret`, ограничивать тело запроса до 256 KiB и не журналировать тела/заголовки авторизации. Пример server-блока Nginx, включаемого в существующий `http {}`:

   ```nginx
   server {
       listen 443 ssl;
       server_name bot.example.ru;
       ssl_certificate /etc/letsencrypt/live/bot.example.ru/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/bot.example.ru/privkey.pem;
       client_max_body_size 256k;
       location = /webhook {
           proxy_pass http://127.0.0.1:8000/webhook;
           proxy_set_header Host $host;
           proxy_set_header X-Max-Bot-Api-Secret $http_x_max_bot_api_secret;
       }
   }
   ```

   Получение сертификата и DNS зависят от вашего сервера. Самоподписанный сертификат и входящий HTTP MAX не поддерживает. Другие маршруты публиковать не требуется.
6. Проверьте токен и зарегистрируйте подписку (секрет передается автоматически, вручную вставлять в curl не нужно):

   ```bash
   docker compose run --rm worker python -m app check
   docker compose run --rm worker python -m app subscribe
   ```

   Подписка на `bot_started`, `message_created`, `message_callback`. Если возникнет проблема доверия к API MAX, загрузите нужный официальный CA PEM и смонтируйте его в worker. Пример `compose.override.yaml`:

   ```yaml
   services:
     worker:
       volumes:
         - ./certs/max-ca.pem:/run/certs/max-ca.pem:ro
   ```

   В `.env` задайте `MAX_CA_BUNDLE=/run/certs/max-ca.pem`, пересоздайте worker и повторите проверку. Корневые сертификаты берите из доверенного официального источника; TLS отключать нельзя.
7. Администратор открывает личный диалог и отправляет `/menu`. Сотрудник запускает бота, вводит ФИО; администратор выполняет `/users`, затем `/approve MAX_ID`. После этого сотруднику доступно меню учета времени.

## Команды сотрудника

| Команда/кнопка | Действие |
| --- | --- |
| `/start`, `/menu`, `/help` | Меню и справка; `/start` никогда не начинает смену |
| `/id` | Собственный стабильный идентификатор MAX |
| ФИО либо `/register Фамилия Имя Отчество` | Запрос регистрации |
| `Начать работу` | Открыть смену |
| `Начать перерыв`, `Закончить перерыв` | Перерыв |
| `Завершить работу` | Закрыть смену и активный перерыв |
| `/status` | Текущая смена, ID и время начала |
| `/hours` | Сегодня, неделя и месяц |
| `/hours сегодня`, `/hours неделя`, `/hours месяц` | Один период |
| `/hours 2026-11-01 2026-11-30` | Диапазон: обе даты включены |
| `/shifts` | Последние 30 смен с ID и отметками |
| `/requests` | Свои последние 50 заявок |

Запрос исправления заменяет начало, конец и **весь список перерывов** завершенной смены. Даты — ISO 8601 с явным часовым поясом. Перерывы через запятую, внутри пары разделитель `/`; `-` означает отсутствие перерывов. Обязательно укажите причину после `|`:

```text
/correct 12 2026-11-02T09:00+06:00 2026-11-02T18:00+06:00 2026-11-02T13:00+06:00/2026-11-02T14:00+06:00 | Забыл вовремя завершить смену
```

В текущем варианте исправляются только завершенные смены. Если смена забыта открытой, сотрудник завершает ее сейчас и затем подает заявку с правильным временем; до одобрения действуют исходные отметки. Автоматического закрытия нет. Будущее окончание, пересекающиеся перерывы и пересечения смен запрещены. Если другая заявка уже изменила смену, старая заявка не применяется: администратор отклоняет ее, сотрудник подает новую.

## Команды администратора

| Команда | Назначение |
| --- | --- |
| `/users` | MAX ID, ФИО и статус регистрации |
| `/approve 123456789` | Одобрить/разблокировать зарегистрированного сотрудника |
| `/block 123456789` | Заблокировать доступ; текущая смена остается открытой |
| `/active` | Все незакрытые смены и состояния |
| `/requests` | Последние 50 заявок всех сотрудников |
| `/review 12` | Автор, дата, причина, старые и предлагаемые значения в UTC |
| `/accept 12`, `/reject 12` | Одобрить или отклонить заявку |
| `/report сегодня all` | Командный отчет за день |
| `/report неделя 123456789` | Отчет по одному сотруднику |
| `/report месяц all` | Командный отчет за месяц |
| `/report 2026-11-01 2026-11-30 all` | Произвольный диапазон |
| `/csv 2026-11-01 2026-11-30 all` | CSV за диапазон |
| `/csv сегодня 123456789` | CSV по сотруднику; поддерживаются также неделя и месяц |

CSV: UTF-8 BOM, `;`, CRLF, русские заголовки, длительности `ЧЧ:ММ:СС` (часы могут превышать 24). ФИО защищены от интерпретации как формулы Excel. Файл отправляется через загрузку MAX, публичных URL отчетов нет. Excel с нестандартным региональным разделителем: «Данные → Из текста/CSV → UTF-8 → разделитель точка с запятой».

## Правила и архитектура

`app/max_api.py` и `app/events.py` — адаптер платформы; `app/timecalc.py` — чистые расчеты, `app/service.py` — операции учета, `app/web.py` — прием событий, `app/worker.py` — обработка/отправка, `migrations/` — версионированный SQL. Все операции бизнес-логики выполняются только внутри транзакции. Проверка доступа выполняется на сервере для каждой команды; отправка отложенных персональных данных дополнительно проверяет текущую блокировку.

События идентифицируются по `message.body.mid`, callback — по сочетанию `callback.callback_id`, ID пользователя и времени нажатия, старт — по ID пользователя и timestamp. UNIQUE inbox исключает повторную обработку. Изменение учета и постановка ответа в outbox коммитятся вместе. Кнопка содержит версию последнего состояния: нажатие из старого меню не выполняет новый переход, бот предлагает актуальное меню. Повторные текстовые действия не создают вторую открытую смену/перерыв. События обрабатываются в порядке поступления; устаревшие отметки, нарушающие хронологию, отклоняются и требуют актуального действия либо исправления.

PostgreSQL advisory lock сериализует бизнес-операции, row locks и partial unique indexes дополнительно защищают открытые интервалы. Это сознательно простой вариант для одной организации. Несколько worker-процессов безопасны, но не увеличивают пропускную способность: для отправки также используется общий lock. Сетевые задержки могут задерживать обработку команд; Webhook продолжает быстро сохранять события независимо от worker. Для крупной организации потребуется отдельное проектирование параллелизма с блокировками по сотруднику и общим распределенным лимитером API.

Период отчета — от локальной полуночи первой даты включительно до локальной полуночи после последней даты исключительно, переведенный в UTC. Для каждого завершенного интервала берется пересечение с периодом, из него вычитаются пересечения перерывов. Количество смен — число завершенных смен, имеющих ненулевое пересечение с периодом. Незакрытые смены отображаются отдельно, даже если начались раньше периода. Округления до часов/минут нет; отображение до секунд. Время действий берется из подтвержденного MAX-события, а не из времени обработки очередью.

## Эксплуатация

- Данные PostgreSQL находятся в named volume `postgres_data`. Обычный перезапуск сохраняет смены и перерывы. `docker compose down -v` удаляет данные: не используйте для рабочего экземпляра.
- Перед обновлением делайте резервную копию PostgreSQL; миграции запускаются автоматически и ведут `schema_migrations`. Down-миграции не предусмотрены, восстановление — из резервной копии.
- Очередь и ошибки: `docker compose run --rm worker python -m app queue`, `docker compose logs --tail=100 worker`.
- Для временных ошибок предусмотрены повторные попытки. После 12 попыток outbox помечается failed; после устранения причины: `docker compose run --rm worker python -m app retry-failed`. Повторная отправка снова проверит блокировку. Не повторяйте сообщения до выяснения причины ошибки.
- Логи содержат ID записи очереди, HTTP-код и номер попытки; не содержат токенов, подписанных upload-URL, ФИО и тела сообщений. Логирование запросов HTTPX и access-log Uvicorn отключено. PostgreSQL и reverse proxy также настраивайте без логирования тел и параметров с персональными данными.
- Inbox содержит входящие команды, outbox — ответы и временно CSV; доступ к БД должен быть ограничен. Установите подходящие вашей организации правила резервного копирования и сроков хранения. Не удаляйте ключи inbox, если требуется сохранять защиту от повторной доставки старых событий.
- Внешний MAX не предоставляет подтвержденный ключ идемпотентности для отправки сообщений: сбой после отправки до фиксации `sent_at` может дать повторное сообщение. Учет времени при этом останется однократным.
- Первый администратор задается `ADMIN_MAX_ID`; изменить его права через бота нельзя. При смене ответственного прежняя запись с ролью admin сохраняется: отзовите ее доступ `/block OLD_ID` после изменения настройки и перезапуска, до передачи доступа. Дополнительное назначение администраторов через бота намеренно не предусмотрено.

## Тесты

Тесты используют **отдельную настоящую PostgreSQL**, не SQLite. Указанные таблицы перед каждым тестом очищаются. Никогда не задавайте рабочую БД в `TEST_DATABASE_URL`.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock
pip install -e . --no-deps
docker run -d --name maxbot-test-db \
  -e POSTGRES_USER=maxbot -e POSTGRES_PASSWORD=testpass -e POSTGRES_DB=maxbot \
  -p 127.0.0.1:55432:5432 postgres:16-alpine
# Дождитесь готовности: docker exec maxbot-test-db pg_isready -U maxbot
TEST_DATABASE_URL=postgresql://maxbot:testpass@127.0.0.1:55432/maxbot \
  pytest -q --cov=app
```

Локальный Python-запуск без Compose: настройте `.env` на свою PostgreSQL, выполните `python -m app migrate`, затем в двух терминалах `python -m app web` и `python -m app worker`. Для получения реальных событий по-прежнему требуется доступный MAX HTTPS endpoint.

Результаты выполненной проверки и проверки, требующие настоящего бота: [docs/VALIDATION.md](docs/VALIDATION.md).
