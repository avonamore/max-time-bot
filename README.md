# Учет рабочего времени в MAX

Бот на Python 3.12 и PostgreSQL 17. Интерфейс на русском. Работает в **личном диалоге**: регистрация с одобрением, смены, перерывы, личные итоги, исправления с согласованием и отчеты администратора в Excel CSV. Геолокация, мониторинг активности и расчет зарплаты отсутствуют.

## Документация MAX и выбранная интеграция

Проверено 29.10.2026 по [официальному репозиторию MAX API](https://github.com/max-messenger/api-schema), OpenAPI **0.0.33**, commit `1a4a502fab096aa3a15d83d7ea95667ffb44d2ac`. Изучены `README.mdx` и `schema.yaml`. Сайт `dev.max.ru` недоступен из текущей облачной среды из-за сетевой политики; официальный GitHub-источник доступен. Копию схемы для аудита можно получить именно по указанному commit.

- [Создание бота](https://dev.max.ru/docs/chatbots/bots-create/create), [управление и токен](https://dev.max.ru/docs/chatbots/bots-create/manage), [подключение организации](https://dev.max.ru/docs/maxbusiness/connection).
- [POST /subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions): webhook, `secret`, `update_types`.
- [POST /messages](https://dev.max.ru/docs-api/methods/POST/messages): сообщения в личный диалог через query `user_id`, `inline_keyboard`, кнопки `callback`.
- [POST /answers](https://dev.max.ru/docs-api/methods/POST/answers): подтверждение callback через query `callback_id`.
- [POST /uploads](https://dev.max.ru/docs-api/methods/POST/uploads): `type=file`, затем multipart POST с полем `data` на полученный URL; `type=file,payload.token` в отправляемом сообщении.
- [GET /updates](https://dev.max.ru/docs-api/methods/GET/updates): официально ограничен для разработки. Этот проект использует webhook, рекомендованный MAX для production; polling не включен.

Текущая официальная схема указывает **`https://platform-api2.max.ru`**, а не прежний `platform-api.max.ru`. Токен передается **только** в `Authorization: <token>` без `Bearer`, не в URL. Применяется небольшой HTTP-клиент `httpx`, без зависимости от стороннего SDK. Python-форк в организации MAX в своем README обозначен как неофициальная библиотека, проверенная командой MAX; его установка здесь не требуется.

## Получение учетных данных

1. Подключите организацию/ИП/самозанятого к [MAX для партнеров](https://business.max.ru/self), дождитесь верификации. В актуальном официальном README создание ботов доступно резидентам РФ с таким статусом.
2. Создайте бота, дождитесь модерации. Получите токен в «Чат-боты → Перейти → Расширенные настройки → Настроить» либо через предусмотренный MAX интерфейс «MAX для бизнеса». Храните его в секретах сервера/локальном `.env`, не в Git.
3. Укажите стабильный числовой `user_id` MAX первого администратора в `INITIAL_ADMIN_MAX_ID`. Это **не** номер телефона, имя или `chat_id`.
4. Если ID пока неизвестен: запустите приложение с `INITIAL_ADMIN_MAX_ID=0` (начальное назначение отключено); отправьте боту `/мой_id` в личном диалоге. Команда доступна до одобрения, сообщает только ID отправителя и ничего не одобряет. Впишите полученное значение и перезапустите процессы. Уже созданная ожидающая запись автоматически **не повышается**: выполните ниже описанную команду начального назначения через доверенный доступ к БД. Не угадывайте чужой MAX ID.

Первый администратор создается при **первом обращении нового пользователя**, совпадающего с настройкой. Затем он отправляет `/start`, принимает заявки `/одобрить MAX_ID`, при необходимости назначает второго администратора `/назначить_админа MAX_ID`. Команда проверяет права действующего администратора и требует уже одобренного сотрудника. Для первоначального повышения ранее зарегистрированного ID администратор сервера может выполнить команду из корня проекта (прочитает ID из окружения, не принимает сообщения от пользователей):

```bash
docker compose run --rm worker python -m app bootstrap-admin
```

Не меняйте ID для обхода обычной регистрации. Команда предназначена для первоначального доверенного назначения, не для работы сотрудников.

## Локальный запуск Docker Compose

Нужны Docker с Compose v2 и внешний HTTPS reverse proxy с сертификатом доверенного CA. MAX больше не принимает HTTP webhook или самоподписные сертификаты. Все команды выполняются из корня репозитория.

```bash
cp .env.example .env
# Заполните .env: пароль PostgreSQL и DATABASE_URL с тем же паролем,
# MAX_BOT_TOKEN, INITIAL_ADMIN_MAX_ID, MAX_WEBHOOK_SECRET, MAX_WEBHOOK_URL.
# Секрет webhook: python -c "import secrets; print(secrets.token_urlsafe(48))"
docker compose up -d --build
# База -> миграции -> web и worker. Повторный запуск миграций безопасен.
docker compose logs --tail=100 web worker
curl --fail http://127.0.0.1:8080/healthz
docker compose run --rm worker python -m app check-max
docker compose run --rm worker python -m app subscribe
```

Проксируйте внешний `https://ваш-домен/webhook/max` на `127.0.0.1:8080/webhook/max`. Передавайте заголовок `X-Max-Bot-Api-Secret` без изменения, ограничьте размер тела 64 KiB, не логируйте тело и секрет. `/healthz` проверяет БД и наличие таблицы миграций, но не токен MAX и не работоспособность worker. Порт БД наружу не опубликован. HTTP-порт приложения привязан только к loopback. При повторной подписке учитывайте уже существующие подписки бота: не запускайте одновременно другой обработчик событий или polling. Скрипт не удаляет чужие подписки.

Для корпоративной сети с дополнительным CA положите проверенный PEM в контейнер read-only и задайте `MAX_CA_BUNDLE=/путь/ca.pem`. Клиент дополняет системное хранилище доверия. Для текущего API следуйте официальным требованиям к доверенным сертификатам, включая сертификат Минцифры при необходимости. Не отключайте проверку TLS.

**CSV:** после проверки токена выполните:

```bash
docker compose run --rm worker python -m app upload-host
```

Команда выводит только hostname, не подписанный URL. Внесите точный hostname в `MAX_UPLOAD_ALLOWED_HOSTS` (несколько через запятую) и в сетевой allowlist сервера. Затем `docker compose up -d --force-recreate web worker`. Используются только HTTPS URL официального ответа `/uploads`, без перенаправлений. Токен бота не передается на сервер загрузки. Пустой список намеренно запрещает загрузку персональных данных. Если MAX возвращает неподдерживаемый HTTP URL, бот откажется отправлять CSV; проверьте актуальные требования у MAX. Открытых ссылок или публичных каталогов с отчетами нет.

Чтобы остановить сервисы: `docker compose down`. Не добавляйте `-v`, если нужно сохранить данные. Делайте регулярные резервные копии PostgreSQL; проверяйте восстановление в отдельную БД.

## Запуск Python без Docker

Установите Python 3.12+, `uv` и доступную PostgreSQL 17; создайте отдельную БД и пользователя. Скопируйте `.env.example` в `.env`, укажите в `DATABASE_URL` адрес своей БД (обычно `localhost`, не `db`).

```bash
uv sync --frozen
uv run python -m app migrate
uv run python -m app web
# В другом терминале:
uv run python -m app worker
# После настройки HTTPS:
uv run python -m app check-max
uv run python -m app subscribe
```

Установка воспроизводится из `uv.lock`. Web и worker нужны одновременно. Перезапуск не закрывает смены или перерывы. Миграции версионируются, выполняются под блокировкой и проверяют SHA-256 уже примененных файлов; команды отката с удалением данных не добавлены.

## Использование

Сотрудник запускает бота → вводит ФИО → ждет одобрения. ФИО не является идентификатором. Главное меню:

- «Начать работу» / `/начать`.
- «Начать перерыв» / `/перерыв`.
- «Закончить перерыв» / `/вернуться`.
- «Завершить работу» / `/закончить`.
- «Мой статус» / `/статус`.
- «Мои часы» / `/часы`: сразу сегодня, текущая календарная неделя, месяц.

После действия показываются время события и статус. При окончании смены — полная длительность, перерывы и чистое время. Начальная и конечная даты диапазона включены: `/часы 2026-10-01 2026-10-31`. Неделя начинается в понедельник. `/смены` показывает последние 20 смен с ID. `/помощь` возвращает все команды. Поддерживаются обычные текстовые команды, если клиент не отображает кнопки.

Запрос исправления (время в `ORG_TIMEZONE`, по умолчанию `Asia/Omsk`):

```text
/исправить 17 | 2026-10-28 09:00 | 2026-10-28 18:00 | 2026-10-28 13:00 / 2026-10-28 14:00 | Забыл вовремя отметить начало
```

Все перерывы указываются заново по порядку, через `;`; без перерывов — `-`. Можно исправить и закрыть открытую смену. Окончание не может быть в будущем, перерывы не могут пересекаться или выходить за смену; смены не могут пересекаться. Для неоднозначного/несуществующего времени при переходе на летнее время нужно явное смещение, например `2026-10-25 02:30+02:00`. Сотрудник не может исправлять чужие смены. `/мои_запросы` — последние решения.

Администратор:

```text
/сотрудники
/одобрить 123456
/блокировать 123456
/назначить_админа 123456
/активные
/запросы
/запрос 5
/принять 5
/отклонить 5
/отчет сегодня
/отчет неделя 123456
/отчет месяц
/отчет 2026-10-01 2026-10-31
/csv 2026-10-01 2026-10-31 123456
```

Списки `/сотрудники`, `/активные`, `/запросы` поддерживают номер страницы, по 20 записей. В CSV: MAX ID, ФИО, число смен, длительность, перерывы, чистое время, число текущих открытых смен. Кодировка UTF-8 BOM, разделитель `;`, CRLF, защита текстовых ячеек от формул Excel. Отчет приходит только администратору в личный диалог. Исправления сохраняют автора заявки, время, причину, снимки до/после, решение, администратора и время решения; действия администратора дополнительно пишутся в `audit_log`. Администратор не может согласовать свое исправление: нужен второй администратор.

Блокировка не закрывает открытую смену и не удаляет историю. Повторное одобрение может вернуть доступ. При изменении смены после подачи исправления ее версия меняется; такой запрос нужно отклонить и подать заново.

## Правила расчетов и надежность

- В БД `TIMESTAMPTZ`, расчеты по UTC; отображение и календарные периоды — `ORG_TIMEZONE` (IANA).
- Интервалы полуоткрытые `[начало, конец)`. Отчет обрезает смену и каждый перерыв границами периода, в том числе через полночь. Открытые смены не учитываются в суммах, показываются отдельно как текущее состояние независимо от выбранного исторического периода.
- Время действия берется из миллисекундного timestamp события MAX; событие старше последнего перехода отвергается с предложением исправления. Позднее событие не создает отрицательных интервалов; будущее более чем на 5 минут отвергается. Синхронизируйте часы сервера.
- Все изменения выполняются в транзакциях под одной advisory-блокировкой PostgreSQL; она действует между worker-процессами. Частичные уникальные индексы дополнительно запрещают несколько открытых смен/перерывов. Это консервативное решение для небольшой/средней команды: высокая нагрузка потребует разделения блокировок по сотрудникам с сохранением порядка захвата.
- Входящие события сначала сохраняются в `inbox`, HTTP 200 возвращается после commit. Ключ идемпотентности — `message.body.mid`, `callback.callback_id` либо `(user_id,timestamp)` для `bot_started`. После обработки тело очищается, ключ остается.
- После использования меню nonce меняется: старой кнопкой нельзя открыть следующую смену после закрытия предыдущей. Повторные команды дополнительно проверяют текущее состояние.
- Состояние учета и ответы `outbox` фиксируются одной транзакцией; отправка MAX происходит после commit. При сбое процесса событие либо целиком применено, либо целиком откатится.
- У отправки сообщений MAX нет подтвержденного idempotency key: после сетевого сбоя на границе ответа **сообщение может повториться**, но учет не повторяется. Ошибки 429/5xx/сети повторяются с задержкой и ограничением 12 попыток; `Retry-After` учитывается. 400 при обработке загруженного файла также повторяется. Остальные 4xx требуют диагностики. Числовые коды и ID очереди логируются без URL, токенов, ФИО и тел событий.
- Перед отправкой отложенного ответа/CSV повторно проверяются роль и статус. Заблокированному пользователю не отправляется ранее запрошенный отчет. Файл доступен через поддерживаемый механизм вложений MAX, без собственного публичного HTTP endpoint.

## Проверки

```bash
uv sync --frozen --group dev
# Только отдельная тестовая БД: тесты очищают ее таблицы!
TEST_DATABASE_URL=postgresql://test_user:test_password@localhost:5432/maxbot_test uv run pytest -q
uv run ruff check app tests
uv run ruff format --check app tests
```

Без `TEST_DATABASE_URL` интеграционные тесты явно пропускаются: это не полная проверка. Тесты БД выполняются на настоящей PostgreSQL, не SQLite. Проверяются расчеты, границы дат/DST, переходы, гонки, повторы webhook, nonce, перезапуск соединения, роли, изоляция сотрудников, исправления, аудит, откат транзакции при сбое, очередь повторов, webhook secret и HTTP-контракт файлов MAX. В тестах HTTP MAX подменен транспортом; реальный мессенджер они не эмулируют.

Результаты текущей проверки и оставшиеся проверки с реальным ботом: [docs/VALIDATION.md](docs/VALIDATION.md). Архитектура и эксплуатация: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
